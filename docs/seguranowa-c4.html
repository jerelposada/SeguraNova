Drag & drop de documentos PDF. Upload directo a S3 con presigned URL. Trigger automático al Worker de ingestion al subir.

Pipeline visible: Subido → Procesando → Generando embeddings → Listo. Polling o WebSocket para actualización en tiempo real.
🗂️ Versioning de Documentos
Subir nueva versión sin borrar la anterior. Historial de versiones por documento. El agente siempre usa la versión activa.
🔍 Chunk Preview
Visualizar cómo quedó fragmentado el PDF antes de indexarlo. Ayuda al admin a detectar problemas de calidad en el RAG.
💬 Historial de Conversaciones
El admin ve qué preguntan los empleados y cuáles no tuvieron buena respuesta. Permite identificar documentos faltantes.
📚 Fuentes Citadas
Cada respuesta del agente muestra el documento fuente y la página. El admin puede auditar la calidad de las respuestas.
📋 Audit Log
Registro de quién subió qué documento, cuándo y qué cambios hubo. Requisito enterprise en cualquier sistema de gestión documental.
📈 Métricas de Uso
Consultas por día, documentos más consultados, tiempo promedio de respuesta, tasa de respuestas sin fuente (gap de conocimiento).
🗑️ Eliminar Documentos
Elimina documento de S3 y sus embeddings de pgvector. Soft delete con confirmación. Los chats históricos conservan la referencia.
ADR-001
Aurora PostgreSQL + pgvector en lugar de BD vectorial dedicada
Contexto: El sistema necesita datos relacionales (pólizas, clientes, siniestros, historial, audit log) y embeddings vectoriales para RAG.

Decisión: Una sola Aurora PostgreSQL con pgvector en lugar de RDS + OpenSearch o Pinecone.

Consecuencias: Menor complejidad operacional, un solo punto de conexión, sin sincronización entre BDs. Trade-off: menor performance vectorial vs OpenSearch a escala masiva — aceptable para este dominio enterprise mediano.
✓ ACCEPTED
ADR-002
Semantic Kernel como orquestador del agente
Contexto: Se necesita orquestación de agentes compatible con .NET, con soporte para RAG y herramientas MCP custom.

Decisión: Microsoft Semantic Kernel sobre LangChain (Python) o solución custom.

Consecuencias: Integración nativa con .NET, soporte oficial Microsoft, compatibilidad con Bedrock. Comunidad más pequeña que LangChain pero en crecimiento activo.
✓ ACCEPTED
ADR-003
Amazon Bedrock (Claude) como LLM
Contexto: Stack 100% AWS. Se necesita un LLM con capacidad de razonamiento para decidir entre RAG y MCP Tools.

Decisión: Amazon Bedrock con Claude. Todo el stack permanece en AWS.

Consecuencias: Sin salida de datos a Azure, facturación unificada AWS, latencia óptima en misma región. Trade-off: menor ecosistema de herramientas vs OpenAI.
✓ ACCEPTED
ADR-004
Clean Architecture con separación estricta de capas
Contexto: Múltiples fuentes de datos (RAG, BD relacional, LLM externo, S3). Sistema que debe ser mantenible y testeable.

Decisión: Clean Architecture — Domain, Application, Infrastructure, API. El dominio no tiene dependencias externas.

Consecuencias: Alta testabilidad del dominio sin infraestructura. El agente y MCP Tools viven en Application. Infrastructure maneja Bedrock, pgvector y S3.
✓ ACCEPTED
ADR-005
Amazon Cognito para autenticación y gestión de roles
Contexto: El sistema necesita autenticación con múltiples roles (Admin TI, Empleado, Agente Siniestros) y el stack es 100% AWS.

Decisión: Amazon Cognito sobre solución custom o Auth0.

Consecuencias: Integración nativa con AWS IAM, sin servidor de auth propio, JWT estándar. Trade-off: curva de configuración inicial vs flexibilidad de Auth0.
✓ ACCEPTED
